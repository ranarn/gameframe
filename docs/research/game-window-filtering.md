# Game window detection/filtering for Apply to Window

**Date:** 2026-08-29
**Status:** Answered

## Question

How should GameFrame filter its "Apply to Window" picker (currently `list_visible_windows` in `win32.rs`, which lists every top-level window via `EnumWindows`/`IsWindowVisible`/non-blank title) down to only actual games? How do existing tools in this space — Windowed Borderless Gaming, Special K, Lossless Scaling, and Borderless Gaming forks — do this filtering in practice: swapchain detection, window-class/style heuristics, exclusive-fullscreen flag checks, process metadata (Steam/Epic/GOG), or a combination?

## Findings

### 1. Window-class/style heuristics (widely used, externally checkable)

This is the one category every inspected tool actually uses, because it's the only one that works from outside the target process with plain Win32 calls.

- **Codeusa/andrewmd5 `Borderless-Gaming`** (the canonical open-source Borderless Gaming, GPLv2) enumerates windows in `Native.cs`'s `QueryProcessesWithWindows`, called with two passes over `EnumWindows`:
  - Pass 0 (strict): visible, non-empty `GetWindowRect`, and style has `WS_CAPTION` **and** (`WS_BORDER` or `WS_THICKFRAME`).
  - Pass 1 (loose fallback): visible and style is simply non-zero.
  - It explicitly strips a documented set of style/ex-style bits when making a window borderless (`Border`, `DialogFrame`, `ThickFrame`, `SystemMenu`, `MaximizeBox`, `MinimizeBox`, and ex-styles `ExtendedDlgModalFrame`, `ExtendedComposited`, `ExtendedWindowEdge`, `ExtendedClientEdge`, `ExtendedLayered`, `ExtendedStaticEdge`, `ExtendedToolWindow`, `ExtendedAppWindow`), but this is the *border-stripping* logic, not a "this is a game" filter.
  - **It has no process-name blacklist/whitelist and no "is this a game" detection at all.** The only engine-specific logic found (`Manipulation.cs`) is `IsUnreal()` (checks if the window class name contains "unreal") and a `NeedsDelay()` check for GameMaker's `YYGameMakerYY` window class — both used only to add a startup delay before manipulating the window, not to decide whether to list it.
  - **Conclusion for this tool: it does not filter for "games" at all.** It lists essentially every plausible top-level application window (via the strict/loose two-pass style heuristic) and leaves the human to pick the right one by process name/window title — i.e., it solves exactly the problem GameFrame has today, by not solving it: better window-listing heuristics, not game detection.

- **Microsoft's own "Which windows appear in the Alt+Tab list?"** (Raymond Chen, Old New Thing — this is the canonical, MS-authored description of how Windows itself decides which top-level windows are "real" application windows for switching purposes) documents the standard algorithm:
  1. Walk to the window's root owner via `GetAncestor(hwnd, GA_ROOTOWNER)`.
  2. Find that owner's last active visible popup via `GetLastActivePopup`.
  3. A window qualifies only if it *is* that computed representative window — this collapses owner/owned window chains (e.g. a game's real window plus invisible helper windows) down to one representative per app.
  4. `WS_EX_TOOLWINDOW` / `WS_EX_APPWINDOW` exist specifically so applications can opt a window out of (or into) this list even when the structural rule would decide otherwise — `WS_EX_TOOLWINDOW` windows are excluded from the taskbar/Alt+Tab by convention; `WS_EX_APPWINDOW` forces inclusion.
  5. A separate, related MS devblog post ("How can I detect that my window has been suppressed from the screen by the shell?", Old New Thing, 2020-03-02) gives the additional, now-standard check for windows that are cloaked (hidden by DWM while still reporting `IsWindowVisible() == TRUE` — e.g. UWP windows on another virtual desktop):
     ```c
     BOOL IsWindowCloaked(HWND hwnd) {
         BOOL isCloaked = FALSE;
         return SUCCEEDED(DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED, &isCloaked, sizeof(isCloaked))) && isCloaked;
     }
     BOOL IsWindowVisibleOnScreen(HWND hwnd) {
         return IsWindowVisible(hwnd) && !IsWindowCloaked(hwnd);
     }
     ```
  6. `WS_EX_TOOLWINDOW`/`WS_EX_APPWINDOW` semantics are also directly documented on Microsoft Learn's "Extended Window Styles" page.

  **This is directly applicable to GameFrame today** — `win32.rs`'s `is_listable_window` currently checks only `IsWindowVisible` + non-blank title, which is exactly the gap the cloaking check closes (e.g. suspended/cloaked UWP or Store-app windows can otherwise show up in the picker with a stale title), and the owner/`GA_ROOTOWNER` + `WS_EX_TOOLWINDOW` checks are what would remove floating tool palettes and duplicate owned windows that today's picker also lists.

### 2. Exclusive-fullscreen flag checks (documented, but not usable externally)

- `IDXGISwapChain::GetFullscreenState` (Microsoft Learn) is the only documented API for querying a swap chain's fullscreen/windowed state. It is a **COM method on the swap chain interface itself** — only the process that created the swap chain holds that interface pointer. There is no separate, documented Win32/DWM API that lets an *external* process ask "is HWND X's owner currently in exclusive fullscreen."
- Microsoft's DirectX Dev Blog post "Demystifying Fullscreen Optimizations" explains what exclusive fullscreen actually is (the game takes "full control of the display," bypassing DWM) and how Fullscreen Optimizations largely converts it into borderless-windowed-with-flip-model transparently — but it documents no mechanism for a third-party process to detect another process's fullscreen state. I looked specifically for one and found none in Microsoft's own material.
- **Conclusion:** exclusive-fullscreen flag checks are a dead end for an external, non-injecting tool like GameFrame. Tools that need this signal (Special K, RTSS) get it by running *inside* the target process (via DLL injection/proxying), not by querying from outside.

### 3. Swapchain/DirectX/Vulkan/OpenGL detection — real, but requires being inside the process

- **Special K** (`SpecialKO/SpecialK`, GPLv3, primary source: its own README) is explicit that its injection strategy is timing-driven, not filtering-driven: "CBT Hooks were chosen due to hookchain order... since most graphics APIs on Windows need a window before they can do non-trivial initialization, a CBT hook reliably gets us into the application **before** D3D9/11/12 swapchain creation." Its most common deployment mode is renaming its DLL to `dxgi.dll`/`d3d11.dll`/`d3d9.dll`/`d3d8.dll`/`ddraw.dll`/`dinput8.dll`/`OpenGL32.dll` and dropping it beside the game executable, so Windows' own loader "catches a ride" via the game's own `LoadLibrary`/static-import of that exact system DLL. In other words: **its "is this a game" signal is implicit and in-process** — it only activates once (and because) the target process itself loads a graphics-API DLL it is impersonating. That's a real swapchain-adjacent signal, but it is fundamentally an in-process technique (proxy-DLL loading or global CBT-hook injection), not something queryable from outside.
- For its *global* injection mode (hooking every new top-level-window-creating process via a CBT hook), Special K does **not** rely on swapchain detection at all to decide who to touch — it relies on a user-maintained **whitelist/blacklist** (SKIF's Settings: "Blacklist Patterns," filename/folder patterns joined by `|`; a `whitelist.ini`; or per-game entries in SKIF's own library) plus **Steam library metadata** for auto-populating that library. This is the "process metadata" story below.
- RTSS (RivaTuner Statistics Server) is closed-source, so no primary source is available; secondary sources (Guru3D, its own changelog notes) describe the same shape as Special K: an injected hook layer targeting DirectX/OpenGL/Vulkan presentation entry points, with a user-configurable "Application detection level" (None/Low/Medium), not an external swapchain query. Flagged as secondary — no public source to verify against.
- **Conclusion:** "does the process actually render with D3D/OpenGL/Vulkan" is a meaningful signal in principle, but every tool that uses it does so by running code inside the target process. GameFrame doesn't do code injection today and this research doesn't recommend adding it just for a window picker. A *weaker*, externally-safe approximation exists, though: `CreateToolhelp32Snapshot(TH32CS_SNAPMODULE, pid)` + `Module32First`/`Module32Next` (Microsoft Learn, "Traversing the module list") lets an external process enumerate the DLLs *already loaded* into another process — including whether `d3d9.dll`, `d3d11.dll`, `dxgi.dll`, `opengl32.dll`, or `vulkan-1.dll` is loaded — without injecting anything. This is a real, documented, non-invasive Win32 technique, but note the same MS doc's caveat that the module snapshot "can fail or return incorrect information" if the target's loader data is transiently inconsistent, so it should be treated as a best-effort positive signal, not a hard gate.

### 4. Process metadata / Steam-Epic-GOG install detection

- **Special K's own frontend, SKIF** (`SpecialKO/SKIF`, primary source: `src/stores/Steam/steam_library.cpp`) detects installed Steam games by: querying the registry (`HKCU`/`HKLM`) for Steam's install path, parsing `libraryfolders.vdf` (old and new formats) to enumerate every Steam library folder, scanning each library's `steamapps` directory for `appmanifest_*.acf` files, and extracting the numeric AppID from the filename (`swscanf(name, L"appmanifest_%lu.acf", &appid)`), then reading the manifest for the display name/install directory. This is a legitimate, documented pattern for cross-referencing "is this executable a Steam game" against known installs.
- Community documentation (Epic's own support pages plus reverse-engineering writeups — secondary sources, no Epic-published spec) describes the Epic Games Launcher equivalent: JSON `.item` manifest files under `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests`, each carrying `InstallLocation`, `LaunchExecutable`, and `DisplayName`.
- GOG Galaxy stores its installed-game list under the registry key `HKEY_LOCAL_MACHINE\SOFTWARE\GOG.com\Games` (`Wow6432Node` on 64-bit installs), one subkey per game ID (secondary source: GitHub wiki for the `erri120/GameFinder` project, cross-checked against GOG community forum posts — no official GOG-published spec was found).
- **This exact problem (cross-launcher installed-game detection) already has open-source prior art directly usable from Rust**, which matters for a concrete recommendation: `steamlocate` (actively maintained, Steam-only, locates Steam's install dir/libraries/installed AppManifests), and broader crates like `game-scanner`/`lib_game_detector`/`game-detector` that additionally cover Epic, GOG, Xbox/Microsoft Store, etc. These reimplement the same registry/manifest parsing SKIF and GameFinder use, just in Rust.
- **Conclusion:** process metadata (matching a candidate window's owning process's executable path against known Steam/Epic/GOG install locations) is a real, practical, externally-checkable signal — arguably the *strongest* single signal available to a non-injecting tool, since it doesn't depend on window styles or graphics APIs at all. Its limitation is coverage: it only recognizes games installed through a launcher GameFrame has a scanner for, and misses non-Steam/Epic/GOG executables (indie games run standalone, emulators, browser-based games, itch.io installs, etc.).

### 5. What combination existing tools actually use, synthesized

No tool inspected does "detect games via swapchain/fullscreen alone." The real pattern across all of them:

| Tool | Primary mechanism | Game-specific filtering? |
|---|---|---|
| Borderless Gaming (Codeusa/andrewmd5) | External `EnumWindows` + two-pass style heuristic (strict: caption+border/thickframe; loose: any styled visible window) | **None** — lists all plausible app windows, human picks |
| Special K (proxy-DLL mode) | In-process: proxy DLL loaded via the game's own `LoadLibrary`/import of a graphics-API DLL | Implicit — activates only in processes that load a graphics API DLL, but requires deploying the DLL into that specific game's folder first (not automatic discovery) |
| Special K (global injection mode) | In-process: CBT hook fires on every new top-level window; whether it *does* anything is gated by | Explicit user whitelist/blacklist (SKIF), pre-populated from Steam library scan |
| Lossless Scaling | Closed-source; per its own documentation, defaults to capturing the current foreground/topmost window, with per-game profiles keyed by process name or window title as an override | Weak default (foreground-window capture), explicit per-profile override for precision |
| RTSS | Closed-source; secondary sources describe an injected hook layer over D3D/OpenGL/Vulkan present calls, with a configurable "detection level" | In-process detection level, not externally verifiable |

The common thread: **tools that need certainty (Special K, RTSS) get it by running inside the process; tools that stay external (Borderless Gaming) don't really solve "is this a game" at all — they solve "is this a plausible top-level application window" and leave the final call to the human.** GameFrame, as a non-injecting window manager, structurally matches the Borderless Gaming category, not the Special K category.

## Recommended filtering strategy

Given GameFrame is a Rust `win32.rs` module with no code-injection architecture, the concrete, implementable strategy is a layered one: use only externally-checkable signals, treat none of them as a hard "yes, this is a game" oracle, and let the human make the final pick (as Borderless Gaming does) — just from a *much shorter, cleaner* list than today's raw `EnumWindows` dump.

**Layer 1 — hard filters (exclude, don't just deprioritize).** Apply these to every candidate window before it's even a candidate:
1. `IsWindowVisible` (already present).
2. Non-blank trimmed title (already present).
3. **New:** not cloaked — `DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED, ...)` must be false/zero. This is a one-line addition to `is_listable_window`'s call site and removes UWP/Store-app windows on other virtual desktops that currently leak into the picker with a stale title.
4. **New:** is its own root-owner and, if it has an owner, is that owner's last-active-visible-popup — i.e. `GetAncestor(hwnd, GA_ROOTOWNER)` combined with `GetLastActivePopup`, per Raymond Chen's documented Alt-Tab algorithm — unless `WS_EX_APPWINDOW` is explicitly set. This collapses helper/owned windows down to one entry per application, the same problem today's flat `EnumWindows` list has.
5. **New:** exclude `WS_EX_TOOLWINDOW` windows (unless `WS_EX_APPWINDOW` is also set) — removes floating toolbars/utility windows, per the documented Extended Window Styles semantics.

This layer alone (all four checks are plain Win32/DWM calls, no new dependencies, no elevation, no injection) should shrink today's raw window list to roughly what Alt-Tab shows — a large practical improvement with minimal code, and it's the same shape of fix Borderless Gaming itself never bothered to add (its two-pass style heuristic is a weaker, older version of the same idea).

**Layer 2 — ranking/labeling signals (don't exclude on these; use them to sort games to the top and/or badge them in the UI), in priority order:**

1. **Process metadata / launcher install match (strongest, cheapest once built).** Resolve the window's PID (`GetWindowThreadProcessId`, already available), get its executable path (`QueryFullProcessImageNameW`), and check it against a cached snapshot of known install locations from Steam (via the `steamlocate` crate, which already implements the registry → `libraryfolders.vdf` → `appmanifest_*.acf` walk SKIF's C++ does), plus optionally Epic's `.item` manifests and GOG's registry key if broader coverage is wanted later. A match is a very strong "this is a game" signal and, unlike style/class heuristics, doesn't depend on the game's UI toolkit at all. Cache the scan (installs don't change per-frame) and refresh it lazily (e.g. once per tray-menu open, or on a timer), not on every `list_visible_windows()` call.
2. **Loaded-graphics-API-module check (medium confidence, moderate cost).** `CreateToolhelp32Snapshot(TH32CS_SNAPMODULE, pid)` + `Module32First`/`Module32Next` to check whether the process has `d3d9.dll`, `d3d11.dll`, `dxgi.dll`, `d3d12.dll` (loaded via `dxgi.dll` typically), `opengl32.dll`, or `vulkan-1.dll` loaded. This is the externally-safe analog of what Special K/RTSS actually key off of, without injecting anything — just enumerating already-loaded modules. Treat a failure to snapshot (documented as possible if the target's loader state is transient) as "unknown," not "not a game." This does have real false positives to expect (Electron apps, browsers, and some non-game 3D tools also load these DLLs) — it is a ranking signal, not a filter.
3. **Window-class heuristics (weak, cheap, easy false negatives).** Borderless Gaming's own `IsUnreal`/`GameMaker`-class checks show this only reliably catches specific engines by name and isn't worth building out as a primary signal — at most, use a small, explicitly-labeled list of well-known engine window classes (`UnrealWindow`, `Direct3DWindowClass`, `YYGameMakerYY`, `SDL_app*`, `GLFW*`) as a minor tie-breaker/badge, never as an exclusion.

**Why this order:** Layer 1 is free (no new APIs, immediate correctness win matching what Windows' own Alt-Tab does) and should be shipped regardless of anything else. Of the Layer-2 signals, process-metadata matching is the only one with genuine precision (a Steam/Epic/GOG install match essentially never false-positives), so it should drive primary ranking/badging; the module-enumeration check is a reasonable secondary signal for games not installed through a recognized launcher (itch.io, standalone .exe, emulators) since at least it confirms "this thing talks to a graphics API," which excludes the browsers/editors/chat apps that currently clutter the picker; window-class matching is the weakest and should only ever nudge sort order, never gate the list. None of the three should hide a window outright — a game GameFrame's scanner doesn't recognize and that doesn't (yet) show a graphics DLL loaded (e.g. a game still on its main menu with the renderer not yet initialized) must still be pickable, just not promoted to the top.

## Open questions

- **Lossless Scaling's actual window-selection algorithm is unverified.** It's closed-source with no official technical documentation found beyond marketing/FAQ pages; everything cited above about its "capture the foreground/topmost window by default, override via per-game profile" behavior comes from Steam Community discussion threads (secondary, community-sourced), not the vendor.
- **RTSS's exact detection-level implementation is unverified** for the same reason (closed-source, no official technical writeup beyond changelog-level descriptions).
- **Whether Steam's own in-game overlay uses module-enumeration (Layer 2, signal 2, above) to decide when to activate is unconfirmed** — this research did not find a primary source describing Steam's overlay-injection decision logic (the Steam client is closed-source), so the module-enumeration technique recommended above is presented as a reasoned application of a documented Win32 API, not as "this is what Steam does."
- **Coverage gap not resolved by this research:** none of the layered signals reliably identify a standalone/indie game with no launcher install record, no recognizable engine window class, and a renderer not yet initialized (e.g. still on a splash screen). The recommendation explicitly treats this as an acceptable gap (the window still appears in the list, just unranked) rather than something to solve with additional heuristics, but a future iteration might want a "recently launched, unrecognized .exe" grace-period heuristic — not investigated here.
- **Epic Games' and GOG's manifest/registry formats have no official spec** — the `.item` JSON schema and the GOG registry layout described above are both reverse-engineered by the community; they could change without notice in a launcher update, unlike Steam's `appmanifest_*.acf`/`libraryfolders.vdf` format, which SKIF's own primary-source code confirms handling multiple historical format versions of.
