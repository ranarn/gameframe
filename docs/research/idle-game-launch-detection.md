# Automatic game-launch detection while idle

**Date:** 2026-08-29
**Status:** Partially answered

## Question

While GameFrame sits idle in the system tray, how can it detect that a previously-registered game process has launched, and immediately trigger the same window-reposition + taskbar-autohide effect the hotkey path currently triggers? Compare WMI process-creation event subscription, a toolhelp-snapshot poll loop, and a Win32 window-creation hook (`SetWinEventHook` / `SetWindowsHookEx` CBT hook) on: what each actually detects (process creation vs. window creation), CPU/battery cost (event-driven vs. polling, and at what interval), Windows-specific implementation gotchas — including whether GameFrame's tray-idle state already has a running message loop — and each approach's ability to filter to only the watched game executable(s).

## Codebase grounding

Before comparing approaches, two facts from the existing source change the framing the question poses:

- **GameFrame already runs a live Win32 message loop while idle in the tray.** `src/app.rs`'s `run_event_loop` (called from `run()`) is a `GetMessageW`/`TranslateMessage`/`DispatchMessageW` loop that blocks and pumps for as long as the process is alive — it's what keeps the tray icon, its menu, and the `global-hotkey` crate's hidden window responsive. This is a hand-written Win32 loop, not eframe's own loop (eframe/egui is only spun up separately, and blockingly, when the Settings window is opened — see `open_settings` in `src/app.rs`). So the premise that there is "no window loop actively watching when idle in the tray" does not hold for this codebase as it stands today: a thread with a message queue is already pumping continuously.
- **The hotkey path's actual effect** is `win32::toggle_borderless_on_foreground_window` (strip border, move/resize via `SetWindowPos`, `DwmSetWindowAttribute` for square corners) plus, independently, `win32::toggle_taskbar_autohide` (`SHAppBarMessage`) — both in `src/win32.rs`, both OS-facing and both already exercised only via `GetForegroundWindow()`/an explicit `HWND`, not a PID. Any detection mechanism ultimately needs to produce an `HWND` (or be able to resolve one) before either of these can run.
- `Cargo.toml` currently enables only four `windows-sys` 0.61 features: `Win32_Foundation`, `Win32_Graphics_Dwm`, `Win32_UI_Shell`, `Win32_UI_WindowsAndMessaging`. `Win32_UI_WindowsAndMessaging` already covers everything `SetWinEventHook`/`SetWindowsHookEx` need (see Approach 3). Toolhelp and WMI both need features that are **not** currently enabled (see Approaches 1–2).

## Findings

### Approach 1 — WMI process-creation event subscription

**What it detects:** Process creation, not window creation — same gap the question flags for all approaches, but WMI's own docs draw a further, load-bearing distinction between the *two* WMI mechanisms the question groups together:

- **`Win32_ProcessStartTrace`** (and its parent `Win32_ProcessTrace`) is an *extrinsic* event class backed directly by the kernel trace provider (`Krnlprov.dll`). Microsoft's own "Monitoring Events" walkthrough subscribes to it with a bare `SELECT * FROM Win32_ProcessTrace` — **no polling-interval clause at all** — and separately notes "asynchronous calls allow you to avoid the overhead of polling for data." This is a genuine push notification, not internal polling.
- **`__InstanceCreationEvent WHERE TargetInstance ISA 'Win32_Process'`** is an *intrinsic* event. Every documented example query for it has the form `SELECT * FROM __InstanceCreationEvent WITHIN PollingInterval WHERE TargetInstance ISA 'Win32_Process' AND ...` — the `WITHIN` clause is a caller-supplied polling interval in seconds. WMI itself is polling `Win32_Process` under the hood at that interval and diffing it; it only *looks* event-driven at the call site. This is the same "poll and diff" work as Approach 2, just delegated to the WMI service process instead of done in GameFrame's own process.

So of the two, `Win32_ProcessStartTrace` is the one worth comparing against a true poll loop — `__InstanceCreationEvent` on `Win32_Process` is not meaningfully different from Approach 2 in mechanism, only in which process does the polling.

**Resource/battery characteristics:** `Win32_ProcessStartTrace` is event-driven — no polling loop, no interval to tune, notification arrives as soon as WMI's kernel trace provider sees the process start. `__InstanceCreationEvent`/`Win32_Process` inherits whatever polling cost its `WITHIN` interval implies, paid inside the WMI service (`WmiPrvSE.exe`/`svchost`) rather than GameFrame's own process.

**Implementation complexity/gotchas on Windows:**
- Requires COM: WMI is accessed through `IWbemServices`/`IWbemLocator`, which requires `CoInitializeEx` (or, per the `wmi` crate below, `CoIncrementMTAUsage`) before use.
- Not currently covered by GameFrame's `windows-sys` features — raw COM access would need `Win32_System_Wmi` and `Win32_System_Com` added to `Cargo.toml`.
- The Rust ecosystem has a purpose-built wrapper, the [`wmi` crate](https://docs.rs/wmi/latest/wmi/) (`ohadravid/wmi-rs`), built on the `windows`/`windows-sys` crates. Its `WMIConnection` documents exactly this use case: "If COM is uninitialized when a new WMI connection is created, it will be initialized (using `CoIncrementMTAUsage`)," and its own docs carry a worked example subscribing to `Win32_ProcessStartTrace` via `con.notification::<Win32_ProcessStartTrace>()`. This removes most of the raw-COM boilerplate, at the cost of a new dependency (which itself pulls in the `windows` crate, a second Windows-bindings crate alongside the project's existing `windows-sys`).
- Community reporting (not confirmed on the primary MSDN/Learn pages for `Win32_ProcessTrace`/`Win32_ProcessStartTrace`, which are silent on privilege requirements) commonly asserts that subscribing to the kernel-trace-backed process classes needs elevated/administrator privileges, because the underlying kernel trace session is privileged. GameFrame's `win32.rs` already has a whole reactive-elevation code path (`Win32Error::is_access_denied`, `relaunch_elevated`) for exactly this class of problem elsewhere in the app, but I could not verify from a primary Microsoft source whether `Win32_ProcessStartTrace` specifically requires elevation to subscribe — see Open Questions.
- WMI service startup/first-query latency and its own background overhead (it's a system service, always running, but a cold subscription still goes through the WMI provider host) is a real but undocumented-in-exact-terms cost; no Microsoft page gives a number.

**Filtering:** Both variants can filter to specific processes in the query itself — `WHERE TargetInstance.Name = 'notepad.exe'` (or `ProcessName` for the trace class) — so GameFrame would receive/act on only the watched executable name(s) rather than every process start on the system. This is a real advantage over enumerating everything and filtering client-side.

### Approach 2 — Toolhelp snapshot poll loop

**What it detects:** Process creation, via a point-in-time snapshot: `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0)` plus `Process32First`/`Process32Next` returns the full process list *at the moment of the call* (per Microsoft's own "Taking a Snapshot, Viewing Processes" walkthrough). There is no notification primitive here at all — the snapshot is inert data. Detecting a *new* process requires the caller to take two snapshots at different times and diff the resulting `PROCESSENTRY32` lists themselves (comparing PIDs or `szExeFile` names) — the API gives no assistance with this; it is 100% on the caller.

**Resource/battery characteristics:** Purely a function of the poll interval GameFrame chooses — there is no documented "correct" interval from Microsoft; this is an engineering trade-off the caller owns entirely. A snapshot + full walk of the process list is a real (if fairly cheap) piece of work — enumerating and copying every `PROCESSENTRY32` in the system — done on a timer. Polling at sub-second intervals (e.g. every 250–500ms) to feel "immediate" means paying that walk 2–4 times/second indefinitely while idle in the tray, for as long as GameFrame runs; polling every few seconds is far cheaper but trades away immediacy (a multi-second delay between the game's process actually starting and GameFrame noticing). No Microsoft source quantifies either the walk's cost or a recommended interval — this trade-off is general engineering judgment, not something the docs establish.

**Implementation complexity/gotchas on Windows:**
- Straightforward, well-trodden Win32 API with a canonical Microsoft code sample (`GetProcessList` in "Taking a Snapshot, Viewing Processes").
- Needs `windows_sys::Win32::System::Diagnostics::ToolHelp` — not currently enabled in `Cargo.toml`; per `windows-rs`'s documented namespace-to-feature-flag convention (confirmed via the crate's own README feature lists and GitHub issue discussion — see Sources), the required feature flag would be `Win32_System_Diagnostics_ToolHelp`.
- Needs a timer to drive the loop — either a genuine sleep-loop on a background thread, or (since a message loop already runs, per the Codebase grounding section) a `SetTimer`-driven `WM_TIMER` dispatched through the existing `GetMessageW` loop in `run_event_loop`. Either is a small addition on top of the loop that already exists.
- No inherent race/permission issues: unlike `OpenProcess`, `CreateToolhelp32Snapshot`/`Process32Next` don't require elevated rights to see other users' process names/PIDs system-wide (per-process handles for deeper inspection would, but simple name/PID enumeration doesn't).

**Filtering:** No built-in filtering — every call returns the entire system process list; GameFrame must string-match `szExeFile` against its own watched-executable list itself, once per full enumeration. Simple to implement (it's exactly the kind of exact-name match `is_listable_window`-style pure logic in `win32.rs` already does for other filtering), but it means walking the *entire* process list every poll rather than being told about only the watched process.

### Approach 3 — Win32 window-creation hook (`SetWinEventHook` / CBT hook)

**What it detects:** This is the one approach in the group that can detect *window* creation directly, which is what the question flags as the actual mismatch with process-creation events — GameFrame needs an `HWND` to reposition, and a process launching does not yet have a visible top-level window at the moment it starts.

- `EVENT_OBJECT_CREATE` (0x8000): per the official Event Constants (Winuser.h) reference, "An object has been created. The system sends this event for the following user interface elements: caret, header control, list-view control, tab control, toolbar control, tree view control, and **window** object." Crucially, it fires for a *lot* of UI object creation, not just top-level app windows — caret creation, common-control creation inside any app, etc. — so a callback needs to filter on `idObject == OBJID_WINDOW` and then further check the `HWND` is actually a top-level window belonging to the watched process (e.g. via `GetWindowThreadProcessId`, and typically also checking `GetAncestor(hwnd, GA_ROOT) == hwnd` since not every top-level-looking `HWND` this event fires for is the app's real main window).
- `EVENT_SYSTEM_FOREGROUND` (0x0003): "The foreground window has changed... the `hwnd` parameter is the handle to the window that is in the foreground." This is arguably the better fit for GameFrame specifically: the hotkey path already acts on `GetForegroundWindow()`, so hooking foreground-change events instead of raw object-creation events would fire exactly once when the game's window actually becomes the active window (rather than firing on every incidental UI-object creation across the desktop) and hands back precisely the `HWND` the existing `toggle_borderless_on_foreground_window` code path already expects.
- **`WH_CBT`** (`SetWindowsHookEx`) is the older mechanism, with `HCBT_CREATEWND` firing "before... creating... a window." Per Microsoft's own "Hooks Overview" page, this is process-creation-adjacent trivia only in that it's about to happen — like `EVENT_OBJECT_CREATE`, it is a window-level, not process-level, signal.

**Resource/battery characteristics:** Fully event-driven, no polling. `SetWinEventHook` with `WINEVENT_OUTOFCONTEXT` queues events across process boundaries and delivers them "on the same thread that called `SetWinEventHook`" (per the official reference) — i.e. as ordinary messages pumped through the same loop already running. This is the cheapest of the three approaches at idle: no timer, no periodic work, nothing happens until the OS itself generates the event.

**Implementation complexity/gotchas on Windows:**
- **The client thread that calls `SetWinEventHook` must have a message loop in order to receive events** — this is stated explicitly in the official reference ("Remarks" section). Per the Codebase grounding section above, GameFrame's tray-idle state *already satisfies this* — `run_event_loop`'s `GetMessageW` loop is exactly such a message loop, already running for tray/hotkey purposes. So the premise in the question ("no window loop actively watching") does not force a dedicated hidden message-only window to be spun up here — the hook could piggyback on the loop that already exists, calling `SetWinEventHook(..., WINEVENT_OUTOFCONTEXT)` once before entering it.
- `WINEVENT_OUTOFCONTEXT` specifically avoids the DLL-injection requirement: per the same reference, a hook DLL is only needed for `WINEVENT_INCONTEXT` ("the DLL that contains the callback function is mapped into the address space of the process that generates the event... The hook function must be in a DLL when this flag is specified"). `WINEVENT_OUTOFCONTEXT` needs no DLL. This is a meaningful advantage over the classic `SetWindowsHookEx` *global* hook path: per Microsoft's "Hooks Overview" page, "a global hook procedure can be called in the context of any application in the same desktop as the calling thread, so the procedure must be in a separate DLL module" — a real complexity/deployment cost a pure-Rust, single-EXE app like GameFrame would rather avoid. `SetWinEventHook`/`WINEVENT_OUTOFCONTEXT` sidesteps it entirely.
- Already covered by GameFrame's existing `windows-sys` features: `SetWinEventHook`, `UnhookWinEvent`, `EVENT_OBJECT_CREATE`, `EVENT_SYSTEM_FOREGROUND`, and `SetWindowsHookExW`/`CallNextHookEx` (the CBT alternative) all live in `windows_sys::Win32::UI::WindowsAndMessaging` — the exact namespace `Win32_UI_WindowsAndMessaging` GameFrame already depends on. No new `windows-sys` feature flag is needed for this approach, unlike Approaches 1 and 2.
- Per Microsoft's "Hooks Overview" page: "Hooks tend to slow down the system because they increase the amount of processing the system must perform for each message. You should install a hook only when necessary, and remove it as soon as possible" — a general caution against *global* `SetWindowsHookEx`-style hooks in particular (every message in the system passes through the hook chain); `SetWinEventHook` is architecturally distinct (accessibility/WinEvent infrastructure, not the message-hook chain) and not the subject of this specific warning, but it's still worth registering for the narrowest event range/process scope needed rather than "all events, all processes."
- Reentrancy: the docs warn a hook callback can be reentered by events triggered while it's still processing an earlier one ("Guarding Against Reentrancy") — a real but manageable implementation detail, not a blocker.
- A Rust wrapper crate exists (`wineventhook`, found via docs.rs search) offering "a rusty wrapper over the window event API," which would reduce the raw-FFI surface if desired — not evaluated in depth here since `windows-sys` already exposes the raw calls with zero new feature-flag cost.

**Filtering:** `SetWinEventHook`'s own parameters (`idProcess`, `idThread`) only let the caller scope to processes/threads that already exist at registration time — they cannot pre-filter to "a process with this executable name, whenever it eventually starts," since the target process doesn't exist yet. So in practice this approach must register with `idProcess = 0, idThread = 0` (all processes/threads on the desktop) and filter *inside the callback*: resolve the event's `HWND` to a PID via `GetWindowThreadProcessId`, then resolve that PID to an executable name/path (e.g. `QueryFullProcessImageNameW`, which lives in a different, also-not-yet-enabled namespace, `Win32_System_Threading`) and compare against GameFrame's watched-game list. This is the same "receive broadly, filter client-side" shape as Approach 2, just triggered by an event instead of a timer.

## Recommendation

Grounded strictly in the above: **`SetWinEventHook` with `WINEVENT_OUTOFCONTEXT`, filtering on `EVENT_SYSTEM_FOREGROUND`,** is the best fit for GameFrame's stated constraints, for reasons the Findings establish directly:

1. **It is genuinely event-driven with no polling**, unlike the toolhelp poll loop (which pays a real, tunable-but-nonzero cost at whatever interval is chosen to feel immediate) and unlike `__InstanceCreationEvent`/`Win32_Process` (which is polling internally, just relocated into the WMI service). Only `SetWinEventHook` and the kernel-trace-backed `Win32_ProcessStartTrace` are true push notifications per the sources gathered, and of those two, the WinEvent hook has no unresolved privilege question and no new dependency.
2. **It requires zero new `windows-sys` feature flags** — `SetWinEventHook`, `UnhookWinEvent`, and the event constants all live in `Win32_UI_WindowsAndMessaging`, already a GameFrame dependency. Both other approaches need at least one new feature (`Win32_System_Diagnostics_ToolHelp` for toolhelp; `Win32_System_Wmi` + `Win32_System_Com`, or a whole new `wmi` crate dependency, for WMI).
3. **The "no window loop" premise doesn't apply to this codebase**, per the Codebase grounding section: `run_event_loop` in `src/app.rs` already pumps `GetMessageW` continuously while idle in the tray, which is precisely what the official docs require ("the client thread that calls `SetWinEventHook` must have a message loop"). No dedicated hidden message-only window needs to be created — the hook can be registered on the same thread, before entering the loop that already exists for the tray icon and hotkeys.
4. **Filtering on `EVENT_SYSTEM_FOREGROUND` rather than `EVENT_OBJECT_CREATE`** further narrows the callback's own filtering burden (one event per foreground change, not one per arbitrary UI-object creation across the desktop) and, more importantly, delivers exactly the signal the existing hotkey path already consumes — a foreground `HWND` — meaning the eventual reaction to a matched event can call directly into the same `win32::toggle_borderless_on_foreground_window`/`win32::toggle_taskbar_autohide` functions the hotkey handlers in `src/app.rs` already use, with no new window-manipulation code needed, only a new trigger.
5. Client-side filtering (resolve `HWND` → PID → executable name, compare against the watched-game list) is unavoidable with this approach — `SetWinEventHook` cannot pre-filter to a not-yet-running process by name — but this is no worse than the toolhelp approach's filtering burden, and the cost is paid only on actual foreground-change events (rare, human-timescale) rather than on a fixed timer.

**What the Findings do not settle, and would need resolving before implementation** (kept out of this recommendation deliberately, per the research-only scope of this task): the exact mechanism for resolving a `PID` to an executable name/path for the match (`QueryFullProcessImageNameW` lives in `Win32_System_Threading`, a feature not yet enabled — a small, low-risk addition, but unverified here), and confirming in practice whether `EVENT_SYSTEM_FOREGROUND` alone is sufficient or whether some watched games' launchers mean the *real* game window only becomes foreground well after an earlier launcher window did (which would need `EVENT_OBJECT_CREATE` or a title/class-name re-check, not just foreground-change, to catch reliably).

## Open questions

- **Does subscribing to `Win32_ProcessStartTrace` require administrator/elevated privileges?** The primary Microsoft Learn pages for `Win32_ProcessStartTrace`/`Win32_ProcessTrace` do not state a privilege requirement one way or the other. Secondary sources (community reports) commonly claim it does, tied to the kernel trace provider being privileged, but this was not confirmed against a primary source and should be verified empirically (e.g. by actually subscribing from an unelevated process) before ruling WMI in or out on that basis.
- **`docs.rs/windows-sys/.../fn.SetWinEventHook.html` returned HTTP 404** on every attempt during this research (both `/latest/` and the pinned `0.61.2` path), despite the sibling function `SetWindowsHookExW` resolving correctly in the same module and despite `EVENT_OBJECT_CREATE`/`EVENT_SYSTEM_FOREGROUND` constants resolving in the module index. This is very likely a docs.rs page-generation/caching quirk for this specific symbol rather than the function being genuinely absent from windows-sys (the C ABI is trivial and stable, and the `windows` crate ecosystem and other windows-sys symbols in the same header/module are all present) — but it was not independently re-verified through a mirror, so treat "windows-sys exposes `SetWinEventHook` under `Win32_UI_WindowsAndMessaging`" as highly likely rather than fully confirmed by a page fetch.
- **Exact required `windows-sys` feature-flag names for Approaches 1 and 2** (`Win32_System_Diagnostics_ToolHelp` for toolhelp; `Win32_System_Wmi`/`Win32_System_Com` for raw WMI/COM) are inferred from windows-rs's documented namespace-to-feature convention, not confirmed by a direct docs.rs "required feature" banner for each specific symbol (several attempted fetches of those exact banner pages 404'd or returned incomplete content during this research).
- **No Microsoft source gives a recommended or typical polling interval** for either a toolhelp poll loop or the `WITHIN` clause of an `__InstanceCreationEvent` query. The "sub-second for immediacy vs. battery-friendly" trade-off in the Findings is general engineering judgment applied to the documented mechanism, not something the primary sources state numerically.
- **Whether `EVENT_SYSTEM_FOREGROUND` alone reliably catches every watched game** (vs. needing `EVENT_OBJECT_CREATE` as a fallback for games/launchers where the real game window is never the very first window created, or where focus behavior varies) was not something any source addressed directly — it's a behavioral question about specific games' launch sequences, out of scope for API-documentation research and noted here only as a risk to validate empirically if this approach is pursued.
